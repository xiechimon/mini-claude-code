Lesson 0001 · Turn 速查表

Mini Claude Code · Architecture Lesson

Turn 是一次用户意图的执行边界

约 8 分钟 目标：看见“一轮”背后的完整生命周期，而不是把它误认成一条消息或一次模型调用。

你在终端按下一次回车，看起来只发送了一句话；系统内部却可能经历多次模型推理、并发工具调用、审批、文件修改和最终回复。Turn 就是把这整段工作圈起来的那条边界。

01先建立模型

它比 Message 大，比 Thread 小

一句话：Thread 是持续的对话；Turn 是其中一次用户请求及后续 Agent 工作；Item 是 Turn 中可观察的输入或输出单位。
Thread 一个可持续、可恢复的对话容器，里面有多个 Turn。
Turn 一次用户意图从开始、执行到终态的完整工作单元。
Item 用户消息、Agent 消息、命令执行、文件修改、工具调用等单个事件对象。

所以不要写出这个等式：

Turn ≠ Message
Turn ≠ 一次 LLM HTTP 请求
Turn = 一个用户请求 + 0..N 次推理 + 0..N 个工具动作 + 一个终态

定义来源：OpenAI Docs · Codex App Server 的 Core primitives 与 Lifecycle overview。

02官方协议

App Server 用 Turn 驱动一次 Agent 生命周期

Codex App Server 是双向 JSON-RPC 协议。客户端先建立 Thread，再用 turn/start 发起一轮，并持续消费通知。

1
thread/start创建对话容器，获得 threadId。
2
turn/start提交输入，可覆盖 model、cwd、sandbox、approval 等本轮配置。
3
item/* 与 delta推理、消息、命令、文件变更和工具进度逐步成为可观察事件。
4
steer / approval / interrupt客户端可以在活动 Turn 中追加方向、回答审批或请求中断。
5
turn/completed以完成、失败或中断等最终状态封口。

这层协议的价值不是换一个“轮次”名词，而是提供稳定的相关性 ID、生命周期、流式观察、控制面与恢复边界。UI 不需要知道 ReAct 内部循环了几次，只需理解 Turn 和 Item 事件。

03项目内部

Mini Claude Code 先把 Turn 用作安全事务边界

在交互式 CLI 中，一条普通输入、一个 /plan 任务或一个 /team 任务，都会先汇合到同一个包装器：

Main
  ├─ 选择 react / plan / team
  └─ SnapshotService.runTurn(mode, input, work)
       ├─ 同步 pre-turn snapshot
       ├─ 执行完整 Agent 工作
       └─ finally: 异步 post-turn snapshot

这说明项目把 Turn 定义成用户可理解、可整体撤销的一次任务。Plan 里的 DAG 节点和 Team 里的 Worker 都不是新 Turn，否则快照会碎成大量内部噪声。

关键源码事实

Agent.run() 内部是循环：模型要求工具时，执行工具、把结果放回 history，然后继续下一次模型调用；直到模型不再要求工具才返回。因此一次 ReAct Turn 可以包含很多次模型调用。

继续追踪：Main.java → SnapshotService.java → Agent.java。

04Runtime API

网络层也有 Turn，但它还是精简版骨架

RuntimeApiServer 采用 HTTP + SSE 回放：

1
POST /v1/threadsSQLite 中创建 thread，并记录 thread.created。
2
POST /threads/{id}/turns记录 turn.started，后台执行，立即返回 HTTP 202。
3
Headless Agent运行结束后写一条 message.delta，再写 completed；异常则写 failed。
4
GET /events?after=N按游标回放已持久化事件；响应写完即关闭，不是持续推送连接。
最值得记住的实现边界

当前 Runtime API 的 Thread 主要是事件分组键，还不是 Agent 对话上下文：每个 Turn 都通过 runHeadlessTask() 新建一个 Agent。前一 Turn 的 conversation history 不会自动进入后一 Turn。

同样，Runtime API runner 直接调用 Agent.run()，没有经过交互路径的 SnapshotService.runTurn()。因此“Runtime 协议 Turn”和“快照 Turn”目前只是概念对应，尚未共享同一个生命周期对象。

架构上最自然的下一步，是让一个统一的 Turn 上下文携带 turnId、threadId、mode、取消令牌、快照边界和事件发布器。现在这些责任散落在 Runtime API、SnapshotService 和 Agent runner 中。

06检索练习

用一次回忆把概念钉住

一次 ReAct Turn 内可以发生几次模型调用？

源码追踪挑战：为什么 Runtime Thread 目前不是真正的对话？

从 RuntimeApiServer.runTurn() 追到 Main.runHeadlessTask()。后者每次都 new ToolRegistry() 和 new Agent(...)，没有从 RuntimeThreadStore 读取历史消息。Store 保存的是 thread 行与 event 行，而不是 Agent conversation history。
