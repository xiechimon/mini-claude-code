# ADR-0007：hook 与权限判定保持两层，且 hook 全跑不短路

`PreToolUse` hook 在 `PermissionGate` **之前**独立跑一层，两者不合并。`AgentLoop.permit()` 的顺序固定为
`PreToolUse hook → PermissionGate → 工具执行 → PostToolUse hook`。同一事件上匹配到的多个 hook **全部执行**，
收齐判定后按契约的 `deny > defer > ask > allow` 归并，不在首个判定处短路。

## 为什么不把权限搬进 hook

课程参考解法（`s04_hooks/code.py`）把 s03 的 `check_permission` 整个包成一个 `PreToolUse` hook，循环里只剩
`trigger_hooks("PreToolUse", block)`。这个做法很有说服力——它让「循环不含任何策略」这句话成立得最彻底。

不采用，因为它丢掉的正是契约在这里的核心区分：**hook 的 `allow` 不等于权限的 `allow`**。契约明文规定
`permissionDecision: "allow"` 只跳过权限**提示**，deny/ask 规则仍要求值；反过来 hook 的 `"ask"` 会**强制**弹出
提示，即使会话模式本来会自动批准。也就是说 hook 是权限判定的**输入**，不是权限判定的**替代**。

压成一层之后这套语义无处安放：一个既是 hook 又是权限的函数只能返回二值，`allow` 与「不表态」不可区分，
`ask` 与「拒绝」不可区分。`code.py` 的 `permission_hook` 正是如此——返回 `None` 或字符串，四值退化成两值。

代价是循环里多一层判定，`permit()` 从「一次 gate 调用」变成「hook → gate → 执行 → hook」四步。换来的是
s15 信任边界有地方落：`updatedInput`（hook 改写工具入参）与 `allow` 的「跳过提示但不跳过拒绝规则」都需要
gate 能区分「模型给的输入」和「hook 改过的输入」、「hook 预批准过」和「没人表态」。合并成一层之后这两个
区分连表达的位置都没有。

## 为什么全跑而不短路

`code.py` 的 `trigger_hooks` 遇到首个非 `None` 返回即 `return`，后续 hook 不执行。它的示范注册顺序是
`permission_hook` 在前、`log_hook` 在后——于是**权限一拒绝，审计日志就不打**，恰恰是最需要留下记录的那一次
调用没有记录。

契约的语义是匹配的 hook 全部执行、收齐判定再按优先级归并。照契约走。已实测钉死：把 exit-2 的 freeze hook
注册在审计 hook**之前**跑真实回合，审计日志里依然有被拒绝的那次 `write_file`。

短路还有一个隐性代价：它让「hook 的执行」与「hook 的注册顺序」耦合。用户在 `settings.json` 里调整两个 hook
的先后，会改变第二个 hook 是否运行——这不是配置该有的语义。

## 顺序执行而不并行

契约说匹配的 hook 并行跑。本实现按注册顺序串行跑。差异只在耗时，不在语义:「全跑」这个可观察性质保住了，
而并行需要一个执行器加结果收集，对理解 hook 机制没有增量。

副作用是契约未定义的情形在本实现里有了确定答案：多个 hook 都设 `updatedToolOutput` 时后注册者胜出，
多个 hook 都拒绝时最先注册者的原因胜出。这些都是本实现的选择而非契约要求，已在
`HookDispatcher` 的方法文档逐处标出。

## hook 是不可信输入

`type: "command"` 的 hook 是用户在配置文件里指定的外部进程。它的 stdout 按固定规则解读，解读失败一律降级为
「无判定」——契约规定 schema 校验失败是非阻塞错误，动作继续。

但**降级绝不静默**：每一次降级（解析失败、超时、非 0 非 2 退出、返回未实现的判定）都产出一条走
`systemMessage` 通道的用户可见警告。理由是一条判定失效的 hook 与一条放行的 hook 在运行时无从分辨，
而 hook 的典型用途是当闸门。契约文档自己就警告过这一条：`settings.json` 里打错一个脚本路径会让闸门
静默失效。

这条不适用于「hook 不读 stdin 导致写入失败」——那是合法的 hook 行为（只看环境变量就干活的那种），
被吞掉的只是「对方不想听」这一个信号，真的需要输入却读不到的 hook 会自己失败并通过退出码报告。

## 什么会推翻这个决定

若 s15 的信任边界最终把「hook 判定」与「权限判定」统一成同一套 `PermissionUpdate` 流水线（契约的
`PermissionRequest` hook 已经带 `permission_suggestions` 与 `updatedPermissions`，方向上是有可能的），
两层就成了同一层的两个阶段，届时应重新评估边界画在哪里。

若某一课引入的 hook 数量或单个 hook 耗时使串行执行成为实际瓶颈，需要改并行；那时「多个 hook 改写同一样东西
谁胜出」会从确定行为退回契约的未定义状态，本 ADR 记录的三条隐性约定需要重新表达。
